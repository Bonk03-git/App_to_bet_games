# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

A web app for predicting match scores in the 2026 FIFA World Cup (in Polish: "Predykcje MŚ2026"). Users bet on each match's score and make one bonus pick (tournament winner and top scorer). A leaderboard ranks the users. The UI text and code comments are in Polish, so keep new user-facing strings in Polish.

## Commands

- `npm run dev`: dev server (Next.js)
- `npm run build`: production build (also type-checks)
- `npm run lint`: ESLint (flat config in `eslint.config.mjs`)

There is no test suite.

The app needs `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_ANON_KEY` in `.env*`. These files are gitignored.

## Architecture

- **Stack:** Next.js 16 App Router, React 19, TypeScript, Tailwind v4, Recharts (charts on the progress page), and Supabase (Postgres plus auth). There is no custom backend or API routes. The only server-side code is the Supabase Edge Function `sync-results` (see "Live results").
- **Everything runs on the client.** Pages are `"use client"` components that query Supabase directly through the shared client in `lib/supabase.ts`. Access control comes from Supabase RLS, not from app code.
- **Auth:** users sign in with a login name, not an email. `lib/auth.ts` turns a login into a fake email `<login>@worldcup.local` before calling Supabase auth. To display a nickname, the code strips the `@...` part. Protected pages call `useRequireAuth()` (`lib/useRequireAuth.ts`). It signs out stale sessions and redirects to `/login`. `/` always redirects to `/login`.
- **Supabase tables used:** `matches` (`home_team`, `away_team`, `match_time` as Polish local time without time zone, `home_score`, `away_score`, `is_it_group_phase`, `knockout_winner`, `external_id` = football-data.org match id, `status` = football-data.org status), `predictions` (unique on `user_id,match_id,league_id`, upserted; includes a `points` column), `bonus_predictions` (unique on `user_id,league_id`), `bonus_results` (one row: `winner`, `top_scorer`), `players` (`total_points`, `exact_hits`; no longer read by the app, see Leagues), `leagues`, `league_members`, and the view `league_standings`.
- **Scoring happens in the database.** Since commit "counting points in database", per-prediction `points` and the totals in `players` are computed in Supabase, not in the frontend. The rules are: exact score = 3 points, correct outcome (win/draw/loss) = 1 point, correct bonus winner = 5 points, correct bonus top scorer = 5 points. `lib/scoring.ts` (`calculatePoints`) is an older client-side copy of these rules and is no longer imported anywhere. Results come from the `sync-results` function; admins can still enter or correct them directly in the database.
- **Time-based locking is done on the client, using `match_time`:**
  - A match disappears from the betting list (`app/matches`) once it has started.
  - Other users' predictions appear in `LeaderboardGrid` only after the match starts.
  - Bonus picks close when the first match kicks off (`isTournamentStarted`).
  - Several pages and components duplicate this logic, so keep them consistent when you change it.
- **Leagues (migration `20261110120000_leagues.sql`):** one tournament, many separate rankings. `leagues` (name unique case-insensitively, bcrypt `password_hash` not readable by the app) and `league_members` (`league_id`, `user_id`, `user_email`). Only admins create leagues (RPC `create_league`, checks `is_admin()`; the admin is not auto-joined); anyone joins with the password (RPC `join_league`) and can leave (RPC `leave_league`, deletes their bets in that league). `predictions` and `bonus_predictions` have `league_id`; unique keys are now `(user_id, match_id, league_id)` and `(user_id, league_id)`. Existing players/bets were moved to league "Główna". RLS: bets only in own leagues, others' bets visible only after match/tournament start, insert/update blocked after start. The DB point triggers are unchanged (per prediction row); the ranking reads the view `league_standings` (security_invoker) instead of `players`, which now sums across leagues and is not used by the app. Frontend: `lib/useLeagues.ts` (my leagues, selected league and the "Obstaw wszędzie to samo" toggle, both in localStorage), `components/LeagueSelect.tsx`, page `app/leagues`. The league picker and the toggle live on `matches` (toggle next to the picker), `leaderboard` and `progress`; the `leagues` page only joins/leaves/creates. Because RLS hides others' bets before kickoff, `LeaderboardGrid` gets the 🔒 markers from table `bet_markers` (`league_id`, `user_id`, `match_id`, null = bonus; only who bet, not the score), kept in sync by triggers on `predictions`/`bonus_predictions`, readable by league members and in the Realtime publication, so locks appear live (migration `20261111120000_bet_markers.sql`). With the toggle on, `matches` upserts a bet into all the user's leagues, and joining a league copies bets on upcoming matches (`lib/copyPredictions.ts`).
- **Pages:** `login`, `dashboard` (rules/info), `leagues` (join/leave, admins also create), `matches` (place bets), `leaderboard` (ranking table plus the `LeaderboardGrid` matrix of users × matches), `progress` (points-over-time charts), and `admin` (admins only). Ties in the ranking share a place when users have equal points and equal exact hits.
- **Admin panel (`app/admin`, issue #2):** admins are rows in `public.admins` (added only via SQL Editor); `public.is_admin()` is used in RLS. `lib/useIsAdmin.ts` reads the user's own `admins` row to show the "Admin" link in `Navbar` and to redirect non-admins away from `/admin`, but the real guard is the database: migration `20261106120000_admin_results.sql` lets `authenticated` update only `home_score`, `away_score`, `knockout_winner`, `manual_result` on `matches`, and only when `is_admin()`. Saving in the panel sets `manual_result = true`; `sync-results` then updates only `status` for that match, never the score, until the admin clicks "Oddaj synchronizacji". Admins still bet and appear in the ranking like everyone else. `admins` and `is_admin()` come from migration `20261105120000_admins.sql`.
- **Live results:** `supabase/functions/sync-results/index.ts` (Deno) fetches matches from football-data.org and writes score, `status` and `knockout_winner` to `matches`; DB triggers then recompute points. It only calls the API when a non-finished match started within the last 4 hours or starts within 5 minutes. API matches are linked to DB rows by `external_id`; if it is empty, by kickoff time (to the minute), then by teams already known from linked matches. Two matches with the same kickoff and no `external_id` stay unlinked, so set `external_id` manually when inserting. Only the 90-minute score counts; during extra time the score is not updated.
  - Function secrets: `FOOTBALL_DATA_TOKEN`, `FOOTBALL_DATA_COMPETITION` (e.g. `WC`, `FL1` for Ligue 1), optional `FOOTBALL_DATA_SEASON`, `CRON_SECRET`. Requests without a matching `x-cron-secret` header get 401. Deployed with `--no-verify-jwt`.
  - `pg_cron` job `sync-results` (from `supabase/cron.sql`) calls the function every 10 seconds via `pg_net` (6 API requests per minute; the football-data.org free plan allows 10), reading `project_url` and `cron_secret` from Supabase Vault. The local copy of the cron secret is in `cron.txt` (gitignored).
  - Migration `supabase/migrations/20261007120000_live_results.sql` adds `external_id`/`status`, enables Realtime on `matches`, `predictions` and `players`, and makes the points trigger also fire on `knockout_winner`.
  - Frontend: `leaderboard`, `LeaderboardGrid`, `matches` and `progress` subscribe to Realtime and refetch (each mount uses a unique channel name, because `supabase.channel()` returns an existing channel with the same name while the previous one is still being removed); the grid shows "● NA ŻYWO" for live statuses; `progress` skips live matches in the charts. `LIVE_STATUSES` is duplicated in these files and the function.
  - Current state (2026-11-11): everything above, plus the leagues migrations, is deployed to the Supabase project `Games-predictor`. For testing, the competition is set to `PL` and Premier League matches from 2026-11-21 to 2026-12-01 were inserted with `scripts/fetch-fixtures.mjs` (the old Ligue 1 test matches were removed). Remove the test matches and their predictions and set the competition back before the next tournament.

## Data seeding

`scripts/fetch-fixtures.mjs` is the preferred way to add matches: `node --env-file=.env.local scripts/fetch-fixtures.mjs <competition code> [days]` (needs `FOOTBALL_DATA_TOKEN` in `.env.local`) prints `INSERT INTO matches ... ON CONFLICT (external_id) DO NOTHING` with `external_id` already set and kickoff converted to Polish time, to paste into the SQL Editor. The `FOOTBALL_DATA_COMPETITION` function secret must match the competition, or `sync-results` will not find the matches.

`games.py` is a one-off script. It reads `worldcup.json` (fixtures in English, with local UTC offsets), translates team names to Polish with `deep_translator`, and converts kickoff times to Polish time (UTC+2). It writes `INSERT INTO matches ...` statements to `wynik.sql`. Machine translation produced some wrong names in `wynik.sql`, for example Turkey → "Indyk" (the bird). Check names before you re-seed.

`puchar/` holds STL models of a trophy and is not part of the app.
